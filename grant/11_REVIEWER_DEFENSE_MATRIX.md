# Reviewer Defense Matrix

This matrix is a grant-facing control document. It does not create evidence; it identifies what must be demonstrated before a claim can be used as a fact in the application.

| Reviewer challenge | Required answer | Evidence required | Status |
|---|---|---|---|
| What problem does the project solve? | Clear, bounded Unreal Engine workflow problem with identified user impact. | Project description + concrete workflow definition. | OPEN |
| Why is Unreal Engine central? | Show where UE is part of the actual proposed workflow, not merely mentioned in the narrative. | Demonstrator plan / UE-specific artifact. | OPEN |
| What exists today? | Separate current concept, prototype, and validated functionality. | Repository evidence + dated artifacts. | OPEN |
| What will the grant pay for? | Tie each cost to a work package, deliverable and validation activity. | Budget traceability. | OPEN |
| What makes the approach technically credible? | Explain mechanism and testable assumptions. | Architecture + validation plan. | OPEN |
| What is novel? | Describe specific mechanism or workflow difference; avoid unsupported "first" or "only" claims. | Comparative research/evidence. | OPEN |
| How will success be measured? | Define baseline, metric, target, method and evidence. | KPI/benchmark plan + results when available. | OPEN |
| What could fail? | Name technical, adoption, security and execution risks. | Risk register + mitigations. | OPEN |
| What happens if the main approach fails? | Preserve a reduced/MVP path that still produces a credible research/development result. | Scenario plan. | OPEN |
| Can the results be reproduced? | Specify environment, versions, inputs and procedure. | Reproducibility record. | OPEN |
| Is the project too broad? | Show explicit non-goals and grant-funded boundary. | Project plan. | OPEN |
| Is the funding request inflated? | Demonstrate bottom-up cost model and necessity of every material line. | Budget workbook/evidence. | OPEN |

## Red-team rule

A reviewer objection is not considered answered merely because the narrative sounds persuasive. The answer is complete only when the required evidence or an explicit, honest limitation exists.

## Final status rule

`OPEN` remains `OPEN` until supporting evidence or a documented limitation is attached. Never mark a reviewer risk complete solely through rewriting.
